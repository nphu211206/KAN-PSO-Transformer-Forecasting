# Public Release Staging Guide

This workspace is not safe to publish as a whole. Use
`PUBLIC_RELEASE_MANIFEST.json` as the allowlist for a clean repository or DOI
archive. The manifest is generated by `build_public_release_manifest.py` and
checks the hashes of the primary K06-K09 evidence archives.

Before public deposition:

1. obtain verified author and repository information;
2. choose and approve a project license;
3. include the ETT and efficient-kan licenses and attribution;
4. decide whether dataset/archive redistribution is permitted or whether the
   release should provide hashes and download instructions only;
5. create the clean release from the allowlist, never from a wildcard copy;
6. run all audits and record the final release SHA-256;
7. deposit the immutable archive and insert its DOI in the manuscript.

Explicitly exclude `.venv*`, caches, temporary QA files, browser/LibreOffice
profiles, unrelated PDFs/images, executables, remote-access utilities and any
credential-bearing files.

`PUBLIC_RELEASE_MANIFEST.json` is a staging manifest, not a published DOI or a
license grant.

After the manifest passes, create a private staging tree with:

```powershell
python stage_public_release.py --output release_staging_v13
```

The script refuses to overwrite a non-empty staging directory.

Staging v13 contains the audited K09 and K10 evidence registered in the public
manifest. It remains private preparation rather than a licensed public release.
Before deposition, separate the GitHub code release from the large Zenodo
evidence archive and apply the third-party redistribution rules above.
